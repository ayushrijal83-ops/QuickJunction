# Architecture — Milestone 03

Status: foundation (M01), auth/authorization/CSRF/audit core (M02), plus
the menu data layer and menu-management surface (M03). No cart, checkout,
order, payment, recommendation, or AI feature exists yet.

## Shape

```
run.py / WSGI server
      │
      ▼
create_app(config_name)              app/__init__.py
      │
      ├── get_config() + validate()   config.py
      ├── configure_logging()         app/utils/logging.py
      ├── db.init_app() ─────────────┐
      ├── migrate.init_app()          │ app/extensions.py
      ├── csrf.init_app() ───────────┘
      ├── register_error_handlers()   app/utils/errors.py
      └── register_blueprints()       app/routes/
                                      │
                                      ▼
                                   MySQL
```

## Layers and the rule each one obeys

| Layer | Module | Rule |
| ----- | ------ | ---- |
| Configuration | `config.py` | Reads the environment. Imports nothing from `app`. Validates before the app is built. |
| Extensions | `app/extensions.py` | Unbound singletons (`db`, `migrate`). Imports nothing from `app`. |
| Factory | `app/__init__.py` | Wires everything. The only module that knows the assembly order. |
| Routes | `app/routes/` | Blueprints (+ `forms.py` WTForms definitions, `app/templates/` Jinja2 pages). Parse and validate the request, call a service, shape the response. No business rules, no queries. |
| Services | `app/services/` | Business rules and transactions. May use models and utilities. Never touches `flask.request`. |
| Models | `app/models/` | SQLAlchemy tables and relationships. No HTTP, no business rules. |
| Utilities | `app/utils/` | Logging, error handling, shared helpers. Bottom of the dependency order — imports nothing from routes or services. |

Dependencies point in one direction: `routes → services → models → extensions`.
Nothing points back up. This is what keeps the later AI and recommendation
modules callable from a CLI or a background job, not just from a request.

## Application factory

`create_app(config_name)` builds an isolated app per call. That is what lets
the test suite run development, testing and production configurations in the
same process, and what keeps global state out of the codebase.

Order is deliberate: **configuration is resolved and validated before any
extension is attached**, so a missing `SECRET_KEY` or `DATABASE_URL` fails at
startup, not at the first request.

## Configuration

Three classes in `config.py`, selected by `APP_ENV` or by the argument to
`create_app`:

| | `development` | `testing` | `production` |
| --- | --- | --- | --- |
| `DEBUG` | `True` | `False` | `False` (enforced) |
| `TESTING` | `False` | `True` | `False` (enforced) |
| Database | `DATABASE_URL` (MySQL) | in-memory SQLite | `DATABASE_URL`, MySQL required |
| `SESSION_COOKIE_SECURE` | `False` (plain-HTTP localhost) | `False` | `True` |
| Secret | from env | fixed placeholder | from env, ≥32 chars, non-placeholder |
| File logging | on | off | on |

`ProductionConfig.validate()` extends the base check and refuses to start on
a weak secret or a SQLite URI.

## Database

Flask-SQLAlchemy owns the engine; `SQLALCHEMY_DATABASE_URI` comes from
`DATABASE_URL`. Engine options set `pool_pre_ping` and a 280-second
`pool_recycle`, because MySQL closes idle connections and a recycled pool is
cheaper than a connection error in a request.

Alembic (`migrations/`) reads its URL from the live app config at runtime —
`migrations/alembic.ini` contains no credentials by design.

**Seven tables now**: `users`, `audit_logs` (M02); `categories`,
`menu_items`, `ingredients`, `menu_item_ingredients`, `customer_preferences`
(M03). Full entity/constraint/index documentation lives in
`docs/DATABASE.md`; `docs/SECURITY.md` covers the security reasoning.
`app/models/__init__.py` imports every model module so it lands in
`db.metadata` and appears in autogenerated migrations — a model that is
never imported here is silently missing from every migration.

Migration mechanics (`flask db upgrade` from empty → schema, `flask db
downgrade` → empty, re-`upgrade`) were verified against a scratch SQLite
database in both M02 and M03, because no local MySQL server has been
reachable in this environment. **MySQL verification is still pending** —
see `docs/DATABASE.md` and `docs/SECURITY.md` for exactly what that
verification needs to check once a server is available.

## Authentication and authorization

Session-based, not token-based: the session cookie holds one integer (the
user id), signed by `SECRET_KEY`. `app/utils/authorization.py` re-loads the
`User` row from the database on every request rather than trusting
anything cached in the session or sent by the client — a role change or
deactivation takes effect on the user's next request. Full reasoning in
`docs/SECURITY.md` §3–4.

```
app/routes/auth.py      register / login / logout — parses the request,
                         calls the service, flashes a message, redirects
                         │
app/services/auth.py    register_user / authenticate_user — business
                         rules, no flask.request, no flask.session
                         │
app/utils/security.py   password hashing (Argon2id) and policy
app/utils/authorization.py   login_user / logout_user / login_required /
                              require_role — session ↔ User boundary
app/services/audit.py   record_event — the only writer of AuditLog rows,
                         also mirrors to the quickjunction.security logger
```

`app/routes/account.py` (`/account/`, `/account/me`, `/account/staff`,
`/account/admin`) is authorization-foundation, not a feature: it exists so
`login_required`/`require_role` have something real to protect. Later
milestones replace it with actual staff/admin views.

## Menu data layer and menu management

```
app/routes/menu.py         GET /menu, GET /menu/<id> -- public, no login.
                            Every query goes through the two "public" service
                            functions below, which filter unconditionally;
                            there is no code path that reads a price or an
                            availability override from the request.
                            │
app/routes/admin_menu.py   /admin/categories/*, /admin/menu/* -- role-gated
                            (STAFF may view /admin/menu; everything that
                            writes is ADMIN only, enforced by require_role
                            on every route, not by hiding a link)
                            │
app/services/menu.py       create_category / update_category /
                            create_menu_item / update_menu_item /
                            sync_menu_item_ingredients / list_public_* /
                            get_public_menu_item -- validates (including
                            re-validating every enum against its allow-list,
                            since a raw POST can skip the <select>), mutates,
                            returns. No flask.request, no flask.session.
app/models/enums.py         SpiceLevel, DietaryType, Cuisine + enum_column(),
                             the shared CHECK-constraint column factory
```

Category and menu-item admin routes both follow the same shape as auth's
register/login: a WTForms form (`app/routes/forms.py`'s `CategoryForm`,
`MenuItemForm`) validates and re-renders with inline errors on failure; on
success the service call's return value drives which `AuditEvent` fires
(`app/routes/admin_menu.py`'s `_audit` helper), comparing the pre-call
snapshot (`was_active` / `was_available`, captured by the route before
calling the service) against the post-call state to decide between the
generic `*_updated` event and the more specific `*_deactivated` /
`*_availability_changed` one.

Ingredients have no standalone CRUD route: the menu-item form takes a
comma-separated ingredient list, and `sync_menu_item_ingredients()`
normalizes, find-or-creates, and links each name. This was a scope
decision, not an oversight — see the final Milestone 03 report.

## HTTP surface

```
GET  /health                        ->  200  {"status": "ok"}
GET  /register                       ->  200  registration form (HTML)
POST /register                       ->  302 → /login on success, 200 + field errors otherwise
GET  /login                          ->  200  login form (HTML)
POST /login                           ->  302 → /account/ on success, 200/429 otherwise
POST /logout                          ->  302 → /login (CSRF-protected, login required)
GET  /account/                        ->  200  minimal authenticated landing page (HTML)
GET  /account/me                      ->  200  {"username", "role"} JSON, login required
GET  /account/staff                   ->  200  JSON, STAFF or ADMIN only
GET  /account/admin                   ->  200  JSON, ADMIN only

GET  /menu                            ->  200  active-category + available-item list (HTML), public
GET  /menu/<id>                       ->  200 or 404, public (404 hides "exists but unavailable")

GET  /admin/categories                ->  200, ADMIN only
GET/POST /admin/categories/create     ->  ADMIN only
GET/POST /admin/categories/<id>/edit  ->  ADMIN only
GET  /admin/menu                      ->  200, STAFF or ADMIN
GET/POST /admin/menu/create           ->  ADMIN only
GET/POST /admin/menu/<id>/edit        ->  ADMIN only
```

`/health` still reports process liveness only — no version, no environment,
no database check. `/account/*` JSON endpoints never return `password_hash`
or any other credential (`docs/SECURITY.md`).

Error handlers return JSON for every status, including on every HTML route
in the app so far — a known simplification while the whole app is still
four forms; see `docs/SECURITY.md`.

## Room reserved for later work

These directories exist and are empty on purpose — no placeholder logic that
would have to be deleted later:

- `ai/` — local Qwen3-0.6B-Base integration. The model is loaded once at
  process start and called through a service, so a request never blocks on
  a cold load.
- `dataset/` — the hand-built instruction dataset.
- `training/` — LoRA/QLoRA fine-tuning scripts. Kept out of the runtime
  dependency set; training never runs inside the web process.
- `models/` — local weights. Git-ignored; already holds
  `Qwen3-0.6B-Base`.
- The recommendation engine (scikit-learn, TF-IDF + cosine similarity) will
  live in `app/services/` because it is business logic that needs the menu
  and order models. The vectoriser is fitted offline and loaded, not fitted
  per request. `MenuItem` and `CustomerPreference` already share the exact
  same `Cuisine`/`SpiceLevel`/`DietaryType` vocabulary (`app/models/enums.py`)
  specifically so this join needs no translation layer when it's built.
- Cart, checkout, order, and payment models/routes -- explicitly out of
  scope for M03; `MenuItem.price` is the only price that exists anywhere,
  and it is never accepted from a client request (see `docs/DATABASE.md`).

Because services never import `flask.request`, all of the above stay
callable from a script, a scheduled job, or a test.
