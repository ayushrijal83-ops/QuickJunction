# Quick Junction — instruction dataset

> **Four versions exist.**
>
> - **v1** (60 examples, 10 categories) — preserved unchanged as the record
>   of what M07 actually trained on.
> - **v2** (150 examples, 15 categories) — built in M07.1 to fix the M07
>   defect where the model asserted that mismatched items matched.
>   **This is the version the in-use adapter was trained on.**
> - **v3** (200 examples, 13 categories, `data/raw/seed_examples_v3.jsonl`) —
>   authored in M07.2 so that **every** example uses the exact prompt shape
>   `app/services/local_llm.py::build_prompt` emits, which only 13 % of v2
>   did. **Trained in M07.2; evaluated in M07.3; not promoted** — it beat v2
>   on every axis except "not set" handling.
> - **v4** (240 examples, 15 categories, `data/raw/seed_examples_v4.jsonl`) —
>   authored in M07.4 to fix exactly that regression while retaining the 159
>   v3 examples that produced its wins. **Authored and validated; no V4 model
>   has been trained.**
>
> Build any of them with
> `python scripts/build_dataset.py --version v1|v2|v3|v4`; each writes its own
> `data/processed/<version>/` directory plus a `manifest.json` recording
> counts, curation method, duplicate policy and SHA-256s.
>
> The section below describes **v1**. See "Version 2" at the end and
> `docs/AI.md` §11 for v2; `docs/AI.md` §13 for v3; §15 for v4.

Hand-authored instruction data for fine-tuning the local Qwen3-0.6B-Base
model to explain recommendations produced by Quick Junction's deterministic
recommendation engine.

## Purpose

The model's only job is to turn an **already-decided** recommendation into a
sentence a customer can read. It never chooses items, never prices anything,
and never decides dietary safety — `app/services/recommendations.py` does all
of that before the model is invoked (see `docs/AI.md`).

The dataset therefore teaches one narrow behaviour: *given a block of
validated facts, restate them as a short, grounded explanation, and say
nothing that is not in the facts.* Examples that would reward inventing a
dish, a price, or an availability status are deliberately absent — the
`unavailable_items` and `no_recommendations` categories exist specifically to
train the opposite reflex.

## How it was created

Every example was **written by hand** for this project, in a text editor, by
the developer. Specifically:

- No third-party restaurant dataset was downloaded or adapted.
- Nothing was scraped from any website.
- The dataset was **not** bulk-generated by another language model.

Vocabulary is drawn from the project's own enums (`app/models/enums.py`), so
the model is trained on exactly the tokens the application produces:
cuisines (`indian`, `chinese`, `italian`, `continental`, `mexican`, `thai`,
`multi_cuisine`, `other`), spice levels (`none`, `mild`, `medium`, `hot`,
`extra_hot`) and dietary types (`vegetarian`, `vegan`, `eggetarian`,
`non_vegetarian`).

Dish names used in the examples are ordinary restaurant dishes chosen to
illustrate the attribute combinations. They are illustrative training text,
not a menu: the running application always substitutes real `MenuItem` rows
from the database.

## Schema

JSONL, one object per line:

```json
{
  "category": "recommendation_explanation",
  "instruction": "Explain in one or two sentences why this menu item was recommended. Use only the facts provided.",
  "input": "Customer preference:\ncuisine: indian\n...",
  "output": "Paneer Tikka is a strong match because ..."
}
```

| Field | Meaning |
| --- | --- |
| `category` | one of the ten categories below; used to stratify the split |
| `instruction` | the task, phrased as the application phrases it |
| `input` | the validated fact block, in the same layout `build_prompt()` emits |
| `output` | the target explanation — grounded, 1–2 sentences |

`instruction` + `input` deliberately mirror
`app/services/local_llm.py::build_prompt`, so training text and inference
text have the same shape.

## Categories

Six examples each, sixty total:

| Category | Teaches |
| --- | --- |
| `recommendation_explanation` | why an item was recommended |
| `customer_preference_explanation` | restating stated preferences, including "not set" |
| `menu_item_matching` | which preferences an item matches **and which it does not** |
| `dietary_reasoning` | how the dietary filter shaped the result |
| `cuisine_matching` | cuisine match / mismatch |
| `spice_reasoning` | spice level relative to preference |
| `ingredient_reasoning` | explaining a dish from its listed ingredients only |
| `score_explanation` | describing a match label without inventing numbers |
| `unavailable_items` | never suggesting something unavailable |
| `no_recommendations` | saying "nothing suits you" instead of inventing a dish |

## Counts and split

| | Examples |
| --- | --- |
| Raw (`data/raw/seed_examples.jsonl`) | **60** |
| Train (`data/processed/train.jsonl`) | **50** |
| Validation (`data/processed/validation.jsonl`) | **10** |

Five train / one validation per category, so all ten categories appear on
both sides.

Regenerate with:

```bash
python scripts/build_dataset.py
```

The split is **deterministic and content-addressed**: each example is hashed
(SHA-256 over its canonical `instruction`/`input`/`output` JSON), examples are
ordered by that hash within their category, and the first one of each
category goes to validation. There is no RNG and no seed. Re-running on
unchanged input reproduces byte-identical files, and adding a new example
never reshuffles the ones already placed.

## Quality control

Enforced by `scripts/build_dataset.py` (refuses to write on violation) and
re-checked by `tests/test_llm.py`:

1. Every line is valid JSON with non-empty `instruction`, `input`, `output`
   and a recognised `category`.
2. No duplicate examples anywhere, by content hash.
3. No example appears in both splits; the two splits partition the seed file
   exactly — nothing lost, nothing added.
4. Re-running the builder is byte-for-byte reproducible.
5. No secrets or personal data: the file is scanned for `password`,
   `secret_key`, `api_key`, `bearer`, `sk-`, `csrf` and real email domains.

Manual review passes applied while writing:

- Every `output` is checkable against its own `input` — no fact appears in an
  output that is absent from the input.
- No output states a price. The engine owns prices; the model is never given
  one (`ExplanationRequest` has no price field).
- No output recommends an item marked unavailable.
- Outputs stay 1–2 sentences, matching the length the UI expects.

## Limitations

- **Small.** Sixty hand-written examples is enough to shape *style and
  grounding*, not to teach new knowledge. It is a formatting/behaviour tune,
  not a capability tune.
- **Single-turn only.** No conversation, no follow-up questions — the
  application has no chat surface.
- **English only.**
- **Illustrative dish names.** The training dishes are not the deployed
  menu; the model must rely on the facts it is handed at inference, which is
  precisely the behaviour being trained.
- **No adversarial examples.** Prompt-injection resistance is handled by
  input sanitisation in `app/services/local_llm.py` and by the model having
  no authority at all — not by training. That is deliberate: training is the
  wrong layer for a security control.
- **Validation set is tiny** (10 examples, one per category). It is a
  smoke check on coverage, not a statistically meaningful evaluation.

# Version 2 (M07.1) — the version the in-use adapter was trained on

## Why a second version

M07's adapter, trained on v1, asserted that mismatched items matched — for a
customer preferring Indian and hot food it described an Italian, unspiced
pizza as "Italian, which is what you prefer". The cause was dataset balance:
v1 was dominated by strong positive matches, so the implicit lesson was
"assert that everything matches". v2 rebalances toward mismatch reasoning.

## Counts

| | Examples |
| --- | --- |
| Raw (`data/raw/seed_examples_v2.jsonl`) | **150** |
| Train (`data/processed/v2/train.jsonl`) | **120** |
| Validation (`data/processed/v2/validation.jsonl`) | **30** |
| Categories | **15** (two held out per category) |

## Categories

| Category | n | Purpose |
| --- | --- | --- |
| `strong_match` | 10 | genuine full matches (kept deliberately small) |
| `partial_match` | 12 | some preferences met, others not — say which |
| `weak_match` | 10 | barely fits; do not oversell it |
| `cuisine_mismatch` | 12 | the cuisine is not the preferred one |
| `spice_mismatch` | 12 | the spice level is above or below preference |
| `dietary_mismatch` | 12 | restricted item — never present as suitable |
| `ingredient_mismatch` | 8 | explain unsuitability from listed ingredients |
| `multiple_conflicts` | 12 | several preferences fail at once |
| `unavailable_items` | 8 | never suggest something unavailable |
| `no_recommendations` | 8 | say "nothing suits you" rather than invent |
| `correct_explanation` | 10 | accurate explanation naming matches and gaps |
| `contradictory_candidate` | 10 | adjudicate a proposed claim (8 reject, 2 confirm) |
| `history_influence` | 8 | completed orders as a signal |
| `preference_over_history` | 8 | stated preference beats past behaviour |
| `why_not_match` | 10 | explain plainly why something is not highlighted |

**Balance:** 106 of 150 (71%) are mismatch-oriented; `strong_match` is 10
(6.7%). `tests/test_dataset_v2.py::test_6` enforces this so it cannot
silently regress.

`contradictory_candidate` intentionally includes two examples where the
proposed claim is **correct**, so the model does not learn to reject
everything reflexively — the opposite failure mode.

## Quality control

Same guarantees as v1, enforced by `scripts/build_dataset.py` and re-checked
by `tests/test_dataset_v2.py` (22 tests):

1. Valid JSON, non-empty `instruction`/`input`/`output`, recognised
   `category`.
2. No duplicates anywhere (SHA-256 over canonical content); the guard is
   tested by feeding the builder a deliberate duplicate and asserting it
   exits non-zero.
3. No train/validation overlap; the two splits partition the seed file
   exactly.
4. Byte-reproducible rebuild.
5. `manifest.json` SHA-256s must match the files on disk.
6. Every mismatch-category example must actually express disagreement
   (≥90%, with the confirming `contradictory_candidate` examples as the
   documented exception).
7. No example may present a non-vegetarian item as suitable for a
   vegetarian or vegan customer — checked with negation-aware matching, so
   "it is **not** suitable for you" is correctly treated as compliant.

## Manual review applied while writing

- Every `output` is checkable against its own `input`; no fact appears in an
  output that is absent from the input.
- No output states a price.
- No output recommends an unavailable item.
- Every example is internally consistent: no case where the input describes
  a mismatch and the output calls it a perfect match. Contradictions appear
  only in `contradictory_candidate`, where the output explicitly corrects
  the false claim.

## Limitations (v2)

- Still small. 150 hand-written examples tunes behaviour, not knowledge.
- Still single-turn, English-only, illustrative dish names.
- Still no adversarial/prompt-injection examples — that remains an
  input-sanitisation concern (`app/services/local_llm.py`), not a training
  one.
- Validation is 30 examples: enough for coverage checking, not for a
  statistically meaningful metric. Model quality is measured instead by
  `training/evaluate.py` on 8 separately-authored held-out scenarios.
- The rebalance fixed the sycophancy but not fluency — v2 still produces
  garbled or non-sequitur sentences. See `docs/AI.md` §11.5.

# Version 3 (M07.2) — authored and validated, **not trained**

> No V3 adapter exists. `LLM_ADAPTER_PATH` still points at the V2 adapter.
> Full detail in `docs/AI.md` §13.

## Why v3 exists

Measured against the prompt the application actually sends
(`app/services/local_llm.py::build_prompt`), **only 13 % of v2 used the
production prompt shape and only 7 % used its exact instruction string**. V2
was therefore fine-tuned largely on prompts production never sends.

Four v2 categories were also unreachable: `ingredient_mismatch`,
`unavailable_items`, `no_recommendations` and `preference_over_history`
describe situations the app cannot produce, because `ExplanationRequest`
carries no price, ingredients, availability or order history, and the model is
never invoked when there are no recommendations at all.

V3 is authored from the production contract inward. Every example uses the
same instruction string and the same prompt shape production emits, and every
candidate is one the dietary hard filter would actually have kept.

## Composition

| | v1 (M07) | v2 (M07.1) | v3 (M07.2) |
| --- | --- | --- | --- |
| Seed file | `seed_examples.jsonl` | `seed_examples_v2.jsonl` | `seed_examples_v3.jsonl` |
| Examples | 60 | 150 | **200** |
| Categories | 10 | 15 | **13** |
| Train / validation | 50 / 10 | 120 / 30 | **161 / 39** |
| Production prompt shape | partial | 13 % | **100 %** |
| Contrastive groups | — | — | **20 × 3** |
| Trained? | yes | yes | **no** |

| Category | n |
| --- | ---: |
| `full_match` | 26 |
| `cuisine_and_spice_differ` | 20 |
| `match_with_unset` | 20 |
| `cuisine_differs_only` | 16 |
| `spice_differs_only` | 16 |
| `single_attribute_match` | 16 |
| `label_fact_consistency` | 16 |
| `no_cross_dimension_errors` | 14 |
| `dietary_compatible_not_identical` | 12 |
| `no_invented_attributes` | 12 |
| `no_invented_context` | 12 |
| `low_signal_suggested` | 10 |
| `unset_stays_unset` | 10 |

## Contrastive groups and the `group_id` field

V3 adds one optional field to the schema:

```json
{"category": "full_match", "group_id": "contrastive_001",
 "instruction": "...", "input": "...", "output": "..."}
```

Twenty groups of three hold the **customer preference block fixed** and vary
only the candidate item — all-align, one dimension differs, two dimensions
differ. The model sees the same customer with three different candidates and
must say something different about each.

`group_id` is metadata only: the builder's example hash is computed over
`instruction`/`input`/`output` alone, so it does not affect identity,
deduplication or the V1/V2 overlap comparison. It affects one thing — grouped
examples sort last when validation is drawn, so a group is never split across
train and validation. The build fails if one ever is.

## How it was created

Written by hand for this project, exactly as v1 and v2 were: not scraped, not
downloaded, not bulk-generated by another language model. The `input` block is
rendered from the production prompt template so its *shape* is guaranteed
correct; every `output` sentence was written by hand.

## Validation

25 checks, all passing, and **each proven non-vacuous** by re-running it
against a deliberately corrupted copy of the dataset. Permanent versions live
in `tests/test_dataset_v3.py` (29 tests).

Beyond the v1/v2 guarantees, v3 additionally enforces:

- Every `input` matches the production prompt regex, anchored at both ends.
- Every candidate would have survived the dietary hard filter.
- Outputs are unchanged by production's `_sanitise()`.
- An unset preference is never described as matched.
- "All three preferences" is claimed only when literally true.
- A `Suggested` item (similarity 0.0) never asserts a match.
- No cross-dimension confusion — a cuisine is never called a spice level.
- Zero content overlap with v1 and v2.

## Limitations (v3)

- **Untrained and unmeasured.** No V3 model exists, so nothing can be said
  about whether V3 improves generation quality.
- Does not address the fluency defect in `docs/AI.md` §11.5 — that is a
  capacity limit of a 0.6B model under LoRA, not a data problem.
- Still small, still single-turn, still English-only, still illustrative dish
  names.
- 39 validation examples remain a coverage check, not a statistical metric.

# Version 4 (M07.4) — authored and validated, **not trained**

> No V4 adapter exists. `LLM_ADAPTER_PATH` still points at the V2 adapter.
> Full detail in `docs/AI.md` §15.

## Why v4 exists

M07.3 evaluated base/v1/v2/v3 on 25 held-out production-shaped cases. V3 beat
V2 on every axis except one — **"not set"** handling, where V3 made 2 errors
and V2 made none. V3 produced *"rather than the cuisine you set"* when no
cuisine was set, *"you only wanted vegan and mild preferences"* when a cuisine
was set, and *"Fattoush Salad is not set and has no heat"*, leaking the
placeholder as an item attribute.

Measured against the v3 file: **31 of its 41 unset-involving examples narrate
the unsetness, and none teaches silently omitting an unset dimension.** V3
taught the model that an unset preference always requires a remark; the model
obliged and sometimes got the remark wrong.

Separately, 16 v3 examples have item cuisine `other` and **none** verbalise it,
so the model had no learned phrasing and substituted a concrete wrong cuisine.

## Composition

| | v3 | v4 |
| --- | ---: | ---: |
| Examples | 200 | **240** |
| Categories | 13 | **15** |
| Train / validation | 161 / 39 | **195 / 45** |
| Contrastive groups | 20 × 3 | 20 × 3 (retained intact) |
| Unset-involving examples | 41 | **67** |
| …teaching silent omission | **0** | **57** |
| Trained? | yes | **no** |

V4 retains **159 v3 examples byte-for-byte** — every one that carries no unset
preference. Those produced v3's M07.3 wins, and all 20 contrastive groups sit
inside them. The 41 defective examples are dropped and replaced by 81 newly
authored ones.

| New / rebuilt category | n |
| --- | ---: |
| `unset_omitted_silently` | 30 |
| `unset_partial_match` | 16 |
| `cuisine_other_unnamed` | 15 |
| `low_signal_suggested` (rebuilt) | 10 |
| `unset_none_set` | 10 |

## The four authoring rules

1. **An unset dimension is not mentioned at all** — neither its value nor the
   fact that it is unset. The explanation describes only what the customer set.
2. **Sole exception:** when all three are unset there is nothing to compare, so
   `unset_none_set` acknowledges it. That is the one place it is correct.
3. **The literal string `not set` never appears in any output.**
4. **Item cuisine `other` is never named as a concrete cuisine** — deny the
   preferred one ("it is not Indian"), refer to it relationally ("the cuisine
   you chose"), or omit it.

## Validation

29 checks, all passing, **all proven non-vacuous** — including by reinserting
v3's three real failure sentences and confirming each is caught. Zero overlap
with v1 and v2; overlap with v3 is exactly the 159 retained examples; and
**zero overlap with the 25 M07.3 evaluation prompts**, without which the
comparison that will judge v4 would be scoring it on its own training data.

Permanent tests: `tests/test_dataset_v4.py` (24 tests).

## Limitations (v4)

- **Untrained and unmeasured.** No V4 model exists, so nothing can be said
  about whether the fix works. The hypothesis is falsifiable: retrain and
  re-run `training/evaluate_production.py`.
- The correction is a *behavioural* one applied through data. If the model
  instead learns to omit dimensions it should mention, that would be the
  opposite failure — which is exactly what the M07.3 harness would detect.
- Still small, still single-turn, still English-only, still illustrative dish
  names. 45 validation examples remain a coverage check, not a metric.
